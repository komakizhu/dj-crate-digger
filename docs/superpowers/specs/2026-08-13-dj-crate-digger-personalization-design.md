# DJ Crate Digger 个性化推荐设计

日期：2026-08-13

状态：设计已正式确认，待按分阶段实施计划执行

基线：`bc75dc7`（`agent/add-local-playlist-exports-20260810`）

## 1. 目标

DJ Crate Digger 的核心目标从“根据一次请求生成可靠歌单”扩展为“在保持可靠性的前提下，逐渐理解单个 DJ 的品味和实际演出选择”。“越来越懂我”同时包含两种不同的成功：更常推荐用户个人喜欢、愿意收藏或继续挖掘的音乐；更常推荐用户在特定演出中真的会使用的音乐。这两类判断必须分开建模，因为用户可能喜欢一首 UK Dubstep 作品，但不会在婚礼现场播放。

本设计的首个产品范围只服务单个 DJ 的本地私人画像，不做跨用户协同学习，不上传数据，不运行独立推荐服务。系统预留未来自愿匿名贡献的接口语义，但不实现上传路径。该产品范围在实施时拆成第 18 节的 A–D 四个阶段，避免用一个超大改动同时交付全部子系统。

## 2. 必须保留的现有能力

以下能力是个性化功能不能破坏的底座：

- 严格两轮 Markdown 问卷，不增加第三轮强制需求收集。
- 用户语言自动跟随；曲名、艺人、正式版本名和平台名保持官方写法。
- 跨平台发现、逐曲验证、平台策略、版本识别和录音级去重。
- 简要版与丰富版输出、11 列主表、可解释推荐理由和播放顺序设计。
- TXT 与 M3U8 本地导出，以及平台歌单写入前的授权和确认边界。
- 不下载音乐、不提供盗版来源、不绕过登录、付费墙、验证码、反爬限制或 DRM。
- 目标平台缺失时不擅自替换，无法验证时不伪造可用性、版本、BPM 或其他事实。

## 3. 不在第一阶段实现

- 多用户画像、匿名协同学习或集中式反馈后端。
- 神经网络、矩阵分解、强化学习或需要大规模训练数据的模型。
- 自动云同步、账号系统或后台常驻推荐服务。
- 1001Tracklists 全站镜像、大规模持续抓取或任何访问限制绕过。
- 自动修改已经交付的歌单。反馈只影响同一会话中的后续重排和未来推荐。
- 将流媒体、媒体评分、1001Tracklists 使用频率直接写成用户私人偏好。

## 4. 选定的总体架构

采用“分层本地推荐器”，不采用把所有逻辑混入一个大型提示词的方案，也不在第一阶段建设独立本地服务。

```text
两轮问卷
  → 本轮任务简报
  → 多来源候选召回
  → 规范化、平台验证和版本去重
  → 分层证据计算
  → 按输出视图排序
  → 多样性、经典和探索重排
  → 11 列表格与导出
  → 记忆状态和可选反馈邀请

自然语言反馈
  → 曲目/版本定位
  → 有限语义解析
  → 理解置信度判断
  → 当前会话更新或 no_update
  → 本轮品味变化摘要
  → 用户确认或纠正
  → 本地长期事件与画像更新
```

LLM 只负责自然语言理解、有限语义提取和可读解释。曲目验证、版本去重、证据更新、权重上限和重排由明确规则执行。

## 5. 领域边界

### 5.1 本轮任务简报 `Session Brief`

只服务当前 SOP，包含演出场景、观众、目标国家/地区、风格、能量、BPM、熟悉度、经典取向、平台规则和输出模式。本轮任务简报不进入长期记忆。

### 5.2 候选曲证据 `Candidate Evidence`

包含流媒体或发行页事实、版本身份、元数据、经典脉络、1001Tracklists 实战证据和编辑语境证据。它可以用于召回和排序，但不能推导为“用户喜欢”。

### 5.3 私人画像 `Private Profile`

只包含用户本人已经确认的品味和场景使用证据。`taste` 与 `utility` 分开存储，目标市场不作为长期画像维度。

### 5.4 推荐视图 `Recommendation View`

是一次输出快照。不同视图共享同一个已验证、已去重候选池，但按不同目标排序。输出结果不会反向修改私人画像。

## 6. 两轮问卷与语言/地区规则

### 6.1 沟通语言

问卷、状态标签、报告标题、表头和解释文字自动跟随用户使用的语言。沟通语言和目标国家/地区是两个独立字段，不能长期绑定。

### 6.2 第一轮

第一轮保留演出基本事实，并加入目标国家/地区：

```markdown
场景：
目标国家 / 地区：
核心声音方向：
歌曲数量或 Set 时长：
其他限制：
```

用户明确填写时始终采用其答案。留空时，系统可根据沟通语言和用字习惯生成本轮临时市场，并在需求摘要中标记 `language_inferred`。简体中文可默认中国大陆；繁体中文只有在用词证据足够时才区分香港或台湾；普通英文无法可靠指向单一国家时采用“英语国际市场”，不能武断指定美国或英国。

目标市场只服务本轮当地熟悉度、文化语境、编辑来源选择和平台可用性判断，不写入长期记忆。用户的音乐风格偏好可以长期保存，但“这次在英国演出”不能变成永久市场偏好。

### 6.3 第二轮

现有“流行度”拆成两个语义字段，但仍保持第二轮一次收集完成：

```markdown
具体风格：
速度 / BPM：
熟悉度与发现感：热门熟悉 / 平衡 / 小众发现 / AI判断
时代与经典：当代为主 / 少量经典锚点 / 新旧桥接 / 经典优先 / AI判断
输出版本：简要版 / 丰富版
情绪：
SET 能量级或能量走势：
平台与链接要求：
其他：
```

任何普通空白字段都采用合理默认值并在需求摘要中披露，不追加第三轮。

## 7. 输出视图

简要版继续只输出一张动态综合表。丰富版从现有四视图扩展为五个视图，所有视图共享同一个已验证、已去重候选池：

1. DJ 品味优先：用于日常 digging、收藏和个人资料库建设。
2. 现场场景优先：以当前场地、观众、目标市场、时间和能量为主。
3. 风格优先：保留现有风格专项语义。
4. 熟悉度与发现感优先：由现有流行度视图演化而来。
5. 动态综合：当前演出需求主导，同时有限使用会话反馈、长期画像、同行证据和探索。

主表仍严格保持 11 列：

```text
歌名 | 艺术家 | 专辑/EP | 风格 | BPM | 歌曲时长 | 能量级 | 发行时间 | 简介 | 选择原因 | 链接
```

经典、同行实战或编辑语境证据写入“选择原因”，不新增列。第 11 列只放用户允许的流媒体或发行平台直接页面。

## 8. 经典、熟悉度和当前适用性

“经典”不是“当前热门”的同义词。候选记录分别维护：

```yaml
canonicality: foundational | scene_classic | modern_classic | current | emerging
audience_familiarity: high | medium | low | unknown
current_playability: high | medium | low | unknown
heritage_role: root_reference | direct_play | bridge_track | sample_lineage | none
```

建立独立的经典脉络召回，使 Skream 等根源人物和作品能进入 UK Dubstep 请求的候选池。经典曲混入各版本并明确标记，不额外建立“经典与根源”歌单。

“少量经典锚点”只保证候选池覆盖，不保证最终歌单固定名额。最终是否入选仍由用户品味、现场适用性、版本可用性和整体编排决定。

## 9. 私人记忆与存储

### 9.1 默认状态

长期记忆默认关闭。首次出现可保存反馈时，系统询问是否启用本地私人记忆。拒绝后仍可使用当前会话个性化，用户以后可以主动开启。

第一阶段不增加“仅记住品味”或“同时记住场景”的开关。启用后统一保存两类证据，但 `taste` 与 `utility.context` 分层存储、互不污染。

### 9.2 存储位置

私人数据必须位于 Skill 安装目录和 Git 仓库之外的用户私有数据目录。第一阶段不做云同步，只支持查看、手动导出、导入、删除单条事件和彻底清除。

逻辑存储采用两层：

- 反馈事件日志：保存反馈原句、结构化解析、确认状态和时间，不保存完整聊天。
- 可重建画像：从有效事件投影得到，用于快速推荐。

推荐的首版物理格式是 JSONL 事件日志加 JSON 派生画像。该格式可以后续迁移，不视为冻结契约。

### 9.3 保存与衰减

原始确认事件默认长期保留，推荐影响力随时间衰减。衰减在读取时计算，不破坏原始证据。删除一条事件后，系统从剩余事件重建画像。

首版默认衰减规则：个人品味证据半衰期 365 天，普通场景使用证据半衰期 180 天；`actually_used` 证据半衰期 365 天。实际参数可在普通测试和回放评测后调整。

### 9.4 私有边界

- 不上传原始对话、反馈、歌单或画像。
- 不保存精确位置、具体场馆或本轮目标市场。
- `sharing_consent` 的默认语义为 `false`，第一阶段不存在上传实现。
- 手动导出必须明确提示文件包含私人偏好数据。

## 10. 自然语言反馈闭环

### 10.1 用户界面

用户不需要学习内部标签，可以直接说：

- “第 3、7 首我喜欢。”
- “Skream 我喜欢，但今晚不会放。”
- “这三首我会用，第二首版本不对。”
- “前半段太商业，后面几首不错。”
- “这首已经有了，别再推。”

支持序号、曲名、链接或粘贴表格行。没有提及的曲目永远是 `unknown`，沉默不能解释为不喜欢。

### 10.2 有限反馈语义

```yaml
taste: liked | disliked | unknown
utility: would_use | would_not_use | actually_used | unknown
familiarity: already_known | new_to_user | unknown
version_fit: correct | wrong | unknown
scope: current_set | scene_specific | general
reason: optional
interpretation_confidence: 0..1
status: session_only | pending_confirmation | confirmed | rejected | corrected
```

LLM 必须从有限语义中选择；无法可靠解析时返回 `unknown` 或 `no_update`，不能编造用户意图。

### 10.3 理解置信度

“反馈理解置信度”只表示系统是否正确理解这句话，不等于用户偏好的统计置信度。只有达到可操作阈值的高置信度解析才能自动影响当前会话。低置信度解析默认不更新，只放入品味变化摘要供用户纠正。

例如“这首一般”可能指不喜欢作品、版本不对或不适合当前场景，因此必须 `no_update`。如果用户随后确认某个明确摘要，该确认本身会把该事件转为可操作证据。

### 10.4 会话与长期确认时点

长期记忆确认发生在歌单交付之后、用户主动发送一批反馈之后：

```text
输出歌单和导出选项
  → 显示记忆状态与可选反馈邀请
  → 用户主动发送一批反馈
  → 高置信度反馈在当前会话生效
  → 低置信度反馈保持 no_update
  → 系统生成一段“本轮品味变化摘要”
  → 用户统一确认、纠正或拒绝
  → 确认后才写入长期事件日志并重建画像
```

用户回复“保存”才写入长期档案；纠正时先更新摘要再确认；回复“不保存”或不回复时，不写入长期档案。

### 10.5 SOP 收尾文案

每次完整 SOP 结束后固定显示状态，不算第三轮需求收集：

```markdown
### 私人记忆状态
- 长期记忆：已启用 / 未启用
- 本轮反馈：已在当前会话生效 / 无反馈
- 长期画像：等待确认 N 项 / 已确认更新 / 本轮未更新

如果愿意，可以直接告诉我哪些曲目你喜欢、这场会用，或哪些不合适、版本不对。回复序号、曲名、链接或粘贴表格行都可以，也可以像平时聊天一样表达。不回复不会影响本次歌单和导出。
```

本地 TXT/M3U8 导出选项与该状态放在同一个“可选后续”区域。用户可以只选择导出、只提供反馈、两者都做或不回复。

## 11. 加权贝叶斯私人画像

### 11.1 分层结构

私人画像使用 Beta 分布表示正负证据，至少区分：

```yaml
taste:
  track: {}
  version: {}
  artist: {}
  genre: {}
utility:
  scene:
    track: {}
    version: {}
    artist: {}
    genre: {}
```

冷启动采用中性弱先验 `Beta(1, 1)`。细粒度节点证据不足时借用父级弱先验，而不是把外部媒体、同行行为或本轮目标市场写成个人先验。

### 11.2 初始证据强度

```text
liked          → taste 正向 +0.5
disliked       → taste 负向 +1.0
would_use      → 对应场景 utility 正向 +1.0
would_not_use  → 对应场景 utility 负向 +1.0
actually_used  → 对应场景 utility 正向 +2.0
wrong_scene    → 对应场景 utility 负向 +1.0，不更新 taste
wrong_version  → 版本适配负向 +1.0，不自动更新作品或流派 taste
```

有效证据在读取时计算：

```text
effective_weight
  = base_signal_weight
  × interpretation_confidence
  × time_decay
  × scope_match
```

含小数权重的更新称为“Beta-based weighted evidence update”，不宣称是最基础的一次观测加一的 Beta-Bernoulli 后验。

### 11.3 最具体层更新与弱向上泛化

反馈主要更新最具体对象，向父级只产生弱影响。首版默认：直接对象系数 1.0，父级系数 0.25，祖父级系数 0.10。评价某个 remix 时，版本层获得主要更新；作品或艺人获得弱影响；流派只获得非常弱影响。场景反馈不能污染个人品味。

例如“我喜欢 Skream，但这个 remix 不适合今晚婚礼”应得到：

- Skream 或具体作品 taste 弱正向。
- 当前 remix 的版本适配负向。
- 婚礼场景 utility 负向。
- UK Dubstep 流派不产生大幅负向变化。

## 12. 候选召回与排序

### 12.1 候选召回来源

- 本轮风格、场景、地区、能量和熟悉度需求。
- 用户已确认的私人画像。
- 经典脉络与根源关系。
- 相似 DJ 的公开 1001Tracklists set。
- 编辑媒体的历史、地区和探索语境。
- 现有流媒体、发行平台、厂牌和元数据来源。

### 12.2 硬门槛

排序前先执行现有安全和事实门槛：平台策略、直接页面验证、曲目/版本身份、版本去重和录音级去重。候选不能凭个性化高分越过验证门槛。

### 12.3 首版视图权重

以下是首版默认值，不冻结为永久契约。每组归一化为 100%。

| 视图 | 当前任务 | 当前会话反馈 | 长期画像 | 同行实战 | 探索 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 现场场景优先 | 70% | 15% | 5% | 5% | 5% |
| DJ 品味优先 | 20% | 20% | 35% | 10% | 15% |
| 动态综合 | 60% | 15% | 10% | 10% | 5% |

风格优先和熟悉度优先沿用各自专项目标，但通过同一证据接口排序。动态综合中的长期画像硬上限为 10%，同行实战硬上限为 10%。只有 DJ 品味优先视图允许长期画像提升到 35%。

编辑语境不是额外叠加的顶层权重。它只修正当前任务中的经典性、地区语境和探索子特征，对单曲最终分数的绝对影响不超过 5 个百分点，总分仍归一化为 100%。

### 12.4 多样性、探索和编排

排序后使用确定性多样性重排，例如 MMR 或等价规则，限制同艺人堆叠、重复版本和单一风格垄断，并兼顾播放段落与能量走势。

探索曲采用可退让软比例：现场歌单通常约 5%–15%，DJ 品味歌单约 15%–25%。当探索候选验证失败、版本不明或明显不适合场景时，可以低于该范围，甚至为零。软比例不是固定名额。

## 13. 1001Tracklists 同行实战证据

### 13.1 相似 DJ 来源

用户可以提供参考 DJ，但不是必答项，也不新增第三轮。没有参考 DJ 时，根据本轮曲风和私人画像自动寻找相似 DJ。

首版相似度采用可解释的加权 cosine/Jaccard，不训练模型。维度包括流派、艺人和厂牌、经典/当代取向、BPM/能量、公开 set 的场景与地区、播放段落和转场邻接关系。

### 13.2 获取边界

- 只按需读取无需登录的公开页面。
- 只获取相似 DJ 的近期和代表性 set，限制 DJ、set 和页面数量。
- 使用本地缓存，首版默认 30 天；保存来源 URL、证据日期和抓取时间。
- 不建立全站数据库，不绕过登录、验证码、付费墙、反爬限制或 robots/站点规则。
- 页面结构变化时只替换来源适配器，不改写排序器。

过期缓存可以作为历史召回线索，但必须保留原始日期，不能表述成“当前趋势”。

### 13.3 使用与输出

1001Tracklists 主要扩充候选池，并提供最高 10% 的排序加成。它不进入私人 Beta 画像，也不能覆盖当前演出需求、用户明确反馈和平台验证。

能追溯到具体公开 set 时，可在“选择原因”中写“相似 DJ 实战使用”或“当地 set 出现”。无法可靠核实时，不展示该依据。

1001Tracklists 不可访问时，系统跳过同行证据并继续正常出歌单。

## 14. 编辑语境证据

### 14.1 来源矩阵

全球核心来源：

- 俱乐部与 DJ：Resident Advisor、DJ Mag、Mixmag、Mixmag Asia。
- 综合乐评与经典脉络：Pitchfork、The Quietus、Crack Magazine。
- 地下挖掘与厂牌线索：Bandcamp Daily、Boomkat、Beatportal。

地区来源按本轮目标市场动态启用：

- 中国：WOOOZY 等本地独立场景档案；注意其时效性，不能单独判断当前趋势。
- 日本：ele-king。
- 亚洲其他市场：以 Mixmag Asia 起步，再按目标国家/地区选择相关当地媒体。

来源选择依据是流派、地区和年代匹配度，不把 Pitchfork 或任何单一媒体设为全球审美裁判。Beatportal 等平台关联媒体必须保留来源属性，不冒充独立共识。

### 14.2 可产生的证据

```yaml
canonicality: foundational | scene_classic | modern_classic | current | emerging
historical_role: root_reference | bridge_track | sample_lineage | none
regional_context: []
current_relevance: high | medium | low | unknown
discovery_role: anchor | bridge | exploration | none
source_url: https://...
published_at: YYYY-MM-DD | unknown
```

编辑证据用于候选召回、经典性、根源关系、地区语境和探索判断。媒体评分不直接变成推荐分，也不通过简单投票平均形成“媒体总分”。

### 14.3 输出边界

- “选择原因”可简短写“UK Dubstep 根源作品”或“当地场景媒体持续提及”。
- 第 11 列仍只放用户规定的流媒体或发行平台链接。
- 用户要求查看依据时，另列“编辑语境来源”，不把文章 URL 冒充曲目链接。
- 媒体报道不能证明具体 remix 在目标平台可用。
- 媒体不可访问或无可靠匹配时直接跳过，不阻塞歌单。

## 15. 平台与来源矩阵

### 15.1 可作为最终播放/发行链接的平台

- SoundCloud
- Apple Music
- Spotify
- 网易云音乐
- Bandcamp
- Beatport

用户未指定时，默认链接展示顺序仍为 SoundCloud → Apple Music → Spotify；发现阶段在允许平台间均衡进行。用户指定 `preferred`、`exclusive` 或 `forbidden` 时沿用现有平台策略。

### 15.2 元数据和身份辅助

- MusicBrainz
- Discogs
- 艺人官网
- 厂牌官网或权威厂牌目录

它们可以辅助核对发行、版本和 ISRC，但不能单独替代最终播放或发行链接。

### 15.3 导出能力

SoundCloud、Apple Music 和 Spotify 只有在官方连接器/API 可用且用户授权后，才可创建平台歌单。网易云音乐、Bandcamp 和 Beatport 不预设平台歌单写入能力。六个平台的合规网页链接均可按用户允许范围写入 TXT/M3U8，但网页链接不能冒充原始音频流。

## 16. 故障与降级

| 故障 | 行为 | 禁止行为 |
| --- | --- | --- |
| 1001Tracklists 超时或不可达 | 跳过同行证据，继续其他来源 | 阻塞歌单或虚构 set 依据 |
| 1001Tracklists 页面解析不完整 | 丢弃不完整记录 | 猜测曲名、版本或 DJ |
| 乐评媒体无匹配或不可达 | 跳过编辑证据 | 复制无关评论或用评分代替验证 |
| 平台无法验证准确版本 | 按现有规则排除、替换或明确列入缺失 | 用高个性化分越过验证门槛 |
| 私人记忆关闭或首次使用 | 使用中性弱先验和当前问卷 | 暗中创建长期档案 |
| 派生画像损坏或版本不兼容 | 从有效事件重建；失败则隔离并回到冷启动 | 静默采用部分损坏数据 |
| 反馈对象或含义置信度低 | `no_update`，放入摘要供纠正 | 把 `unknown` 当 `disliked` |
| 语言无法可靠推断国家 | 使用宽泛语言市场并标记推断 | 武断指定国家或写入长期记忆 |

外部证据、长期画像和会话反馈都属于可降级层。两轮问卷、平台验证、版本去重、11 列输出和安全边界始终是核心底座。

## 17. 测试与评测

现有 25 个行为评测和 33 个触发评测全部保留，并按新问卷字段更新受影响的断言。

### 17.1 确定性规则测试

使用固定候选池和固定反馈事件测试：

- Beta 正负证据和加权伪计数。
- `taste` 与 `utility` 隔离。
- 最具体层更新和弱向上泛化。
- 时间衰减、删除事件和画像重建。
- 动态综合长期画像 ≤10%、同行证据 ≤10%。
- 编辑证据单曲影响 ≤5 个百分点。
- 版本识别、录音级去重、多样性和探索软比例。

### 17.2 自然语言反馈语料

测试语料分为：

- 黄金样例：喜欢、会用、不会用、实际用了、不喜欢、版本不对。
- 同义改写：口语、省略、中英文混合、序号、曲名、链接和表格行引用。
- 歧义样例：“一般”“不太行”“这个不对”等，期望 `no_update`。
- 纠正路径：先解析为 `wrong_scene`，用户纠正为 `disliked`，随后按纠正后的事件重建画像。

### 17.3 对话行为评测

至少覆盖：

- 中文沟通但明确英国演出，英文沟通但明确日本演出。
- 未填写地区时使用临时推断且不持久化。
- 两轮 Markdown、第二轮新字段和无第三轮强制问卷。
- 记忆默认关闭、每次 SOP 收尾显示状态。
- 高置信度会话更新、低置信度不更新、摘要统一确认。
- Skream 等经典根源候选进入候选池但不获得固定最终名额。
- 媒体文章和 1001Tracklists 不能替代流媒体版本验证。
- 所有个性化来源不可用时仍保留现有 11 列报告和导出。

### 17.4 连接器测试

1001Tracklists 和媒体适配器使用保存的公开页面样本进行解析测试，不依赖实时网站。少量人工触发的联网冒烟检查页面结构变化和实际降级行为；实时网站不可达不能让普通离线测试失败。

### 17.5 推荐质量回放

建立少量合成 DJ 画像和固定候选池，进行成对比较：同一个 DJ 更换演出场景；同一场景更换 DJ 画像；同一画像加入反馈前后再次排序。

观察指标包括个人喜欢命中、场景会用命中、实际使用命中、平台验证覆盖率、版本正确率、艺人/风格多样性和探索接受率。第一阶段不声称统计显著性，先要求每个标注场景的排序方向正确且理由可解释。

## 18. 分阶段实施顺序

### 阶段 A：交互基础

实现语言跟随、第一轮目标国家/地区、语言缺省推断、第二轮熟悉度/经典字段和 SOP 收尾状态。此阶段不假装已经拥有私人画像，也不提前输出尚未实现的 DJ 品味优先视图。先通过现有问卷、输出、平台和导出回归测试。

### 阶段 B：本地私人记忆

实现事件日志、可重建画像、自然语言反馈解析、会话更新、摘要确认、查看、删除、导入、导出和彻底清除。

### 阶段 C：个性化排序

实现分层 Beta 证据、丰富版五视图、各视图权重、经典脉络召回、多样性与探索重排、解释理由和质量回放。

### 阶段 D：外部证据适配器

实现 1001Tracklists 与编辑媒体的按需适配器、缓存、统一候选证据、降级逻辑和少量联网冒烟检查。

每个阶段分别编写实施计划、完成普通测试和场景评测后再进入下一阶段。A–D 不合并成一个超大实施计划。不新增 hash、冻结 contract、baseline 或独立发布 gate；已有安全措施保持不变。

## 19. 验收标准

设计实现完成时应满足：

- 用户不填写地区时可得到明确标记的临时市场；填写地区时不会被语言推断覆盖；市场不会出现在长期档案中。
- 用户可用自然语言反馈，无需学习内部标签；沉默和歧义不会产生负面画像。
- 当前会话反馈自动生效，长期档案必须经一轮摘要统一确认。
- 删除反馈事件后，派生画像能从剩余事件重建。
- “喜欢但这场不会用”能同时产生 taste 正证据和该场景 utility 负证据。
- 动态综合中长期画像和同行实战各自不超过 10%；编辑证据不超过 5 个百分点。
- 经典根源曲能进入候选池，但不会因固定配额强行进入最终歌单。
- 1001Tracklists 和媒体来源不可用时，系统继续完成验证歌单。
- 媒体文章与 1001Tracklists 不出现在第 11 列，也不能替代平台版本验证。
- 简要版、丰富版、11 列表格、两轮 Markdown、平台策略、版本去重和 TXT/M3U8 安全导出继续成立。
